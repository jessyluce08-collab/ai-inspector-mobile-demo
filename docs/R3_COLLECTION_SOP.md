# Procédure de collecte — pas d’exécution avant autorisation

## Avant la première invitation

1. Compléter les champs de l’investigateur, décider des obligations applicables, approuver les limites opérationnelles et les documents français. La conservation antérieure proposée de 90 jours n’est pas une politique approuvée : inscrire la politique réellement choisie.
2. Effectuer l’unique ticket de vérification finale : approuver puis horodater/enregistrer prospectivement protocole, version d’analyse et verrou ; produire la variante pilote autorisée et son empreinte exacte. Vérifier son parcours/export technique et la compatibilité du validateur. Aucun ancien résultat technique ne rejoint ce pilote.
3. Publier uniquement le nouveau dossier pilote versionné, après décision du responsable. Préserver index.html racine et les deux dossiers existants. Vérifier le fichier réellement servi contre le verrou. Les volontaires reçoivent l’URL HTTPS directe, pas une page GitHub ni une pièce jointe iOS.
4. Conserver un registre privé par code : consentement/version/date, admissibilité, retrait et, si disponible, état de démarrage/retour du fichier. Ne pas déduire l’absence de tentative d’une absence d’export. Ce registre fournit les dénominateurs de personnes contactées/consentantes ; les JSON seuls ne le peuvent pas. Six codes consentants au maximum, sans remplacement de fichiers jugés décevants.

## Pendant une session

Le volontaire lit les informations et coche le consentement de la variante pilote. Il utilise son code PILOT-…, affiche A et B avant A/B/T et répond aux24 comparaisons. U reste distinct de l’absence de différence. Pas de correction, retour en arrière ou consigne donnant la réponse attendue. Si le rendu ne permet pas de juger : U ou arrêt, sans contourner le garde-fou. Ne pas demander de diagnostic systématique ni de changement de zoom à répétition.

Ne pas rafraîchir/fermer l’onglet avant export ; il n’y a pas de sauvegarde persistante. À la fin, télécharger le **résultat** JSON, vérifier sa présence puis le partager volontairement selon la notice. En cas d’échec, réessayer l’export ou utiliser l’affichage JSON. Ne jamais remplacer le fichier par une capture d’écran. En cas d’arrêt, conserver l’export partiel si le volontaire accepte de le remettre.

Diagnostic supplémentaire seulement pour un incident précis : activer « Diagnostic d’affichage · test technique », exporter ce fichier séparé et expliquer les mesures conservées. Son data_class est TECHNICAL_DIAGNOSTIC_NOT_HUMAN_OBSERVATIONS. Ce n’est ni le fichier de réponses ni un consentement, et il n’est pas nécessaire pour une session ordinaire. Ne pas rouvrir le chantier géométrie sans défaut critique reproductible.

## Réception et contrôle hors ligne

Stocker les originaux non modifiés dans l’espace restreint annoncé. Séparer fichiers, registre de consentement et éventuelle correspondance nominative. Ni dépôt GitHub public ni dossier synchronisé partagé sans maîtrise des accès. Enregistrer la réception, le code et l’empreinte SHA256. Les exports peuvent contenir des métadonnées techniques ; ne pas les qualifier d’anonymes.

Suivre research/r3_pilot/README.md pour la commande d’analyse. Le mode technique par défaut ne produit pas un jeu pilote. Le mode pilote exige verrou autorisé, configuration approuvée et registre privé. Un code de sortie 2signale un fichier invalide ou un conflit avec rapport produit  ; 1signale une configuration refusée  ; 0ne signifie pas qualification scientifique. Consulter chaque ligne de report.json, pas seulement le code de sortie.

Conserver les fichiers malformés/incompatibles pour vérification privée si la politique autorise leur conservation. Redemander le même export si approprié, sans nouvelle session ni retouche du JSON. Une session partielle n’est pas effacée du bilan de faisabilité. Un doublon exact ou une nouvelle tentative d’export n’est pas un deuxième volontaire. Deux contenus incompatibles sous le même identifiant de session sont mis en quarantaine, sans choisir le plus favorable. Un second essai par code reste tracé mais n’est pas ajouté. Un fichier manquant n’est jamais fabriqué : le bilan de non-retour repose sur le registre.

Appliquer les demandes de retrait et la date de suppression annoncée ; ne pas invoquer la traçabilité pour empêcher un retrait. Rapporter seulement des résultats agrégés proportionnés au petit effectif et ne pas publier les diagnostics/lignes individuelles. Arrêter selon le protocole même en cas de non-retour ou de résultats inattendus.
